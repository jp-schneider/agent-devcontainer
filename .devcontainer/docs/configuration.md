# Configuration

How the container works under the hood. To get started, see [getting-started.md](getting-started.md); for how-tos
(extensions, packages, mounts), see [customizing.md](customizing.md). Protections: [security.md](security.md).

## How it is composed

A variant is a list of compose files, merged in order:

```
shared/compose.core.yml          always first: hardening, workspace, Claude config, network
shared/compose.gpu.yml           optional: NVIDIA GPU + CUDA base image
shared/compose.docker-proxy.yml  optional: read-only Docker API (see below)
shared/compose.lmstudio-host.yml     optional, one of: local LM Studio on the host (see below)
shared/compose.lmstudio-sidecar.yml                     or as a sidecar container
shared/toolchains/<name>/compose.yml   toolchains, zero or more: volumes, environment
../.generated/compose.node.yml     node toolchain only: node_modules volumes, generated by its init-host.sh
compose.project.yml                yours: mounts, services, resources (see customizing.md)
../.generated/compose.host.yml     generated per host by initialize.sh
../.generated/compose.protect.yml  always last: read-only protection, generated by initialize.sh
```

- **`shared/Dockerfile`**: one Dockerfile for all variants, parametrized by `BASE_IMAGE` and `TOOLCHAINS`.
- **`shared/initialize.sh <variant> [<toolchain>...]`**: runs on the host before every start. It writes
  `shared/.env` with paths, UID/GID, the compose project name and the toolchain list. It also runs
  each toolchain's `init-host.sh` and generates both overlays.
- **`.generated/compose.resolved.yml`**: the fully merged config of the last started variant
  (`docker compose config`), for inspection. It isn't used to start the container, and the
  devcontainer CLI adds its own overrides on top. `env_file` contents (`container.env`) are
  inlined, so treat it like `container.env`.
- **`compose.core.yml` must stay first:** compose loads `.env` from the first file's directory.
  `shared/.env` is used only for that interpolation. It is **not** passed into the container;
  overlays pass the variables the container needs explicitly.

## Environment files

| File | Visible in the container | Use for |
|---|---|---|
| `container.env` | yes, as environment variables and as a file | anything the container needs (API endpoints, tokens you accept the agent can read) |
| `.env`, `.env.*`, `*.env` and other secret files (see below) | **no** (masked, appear empty; the host copy is unchanged) | host-only config and secrets; `DEVCONTAINER_*` lines are usable in `compose.project.yml` |

Both are gitignored, and `initialize.sh` creates them empty if missing.

**Masked files** are defined by regexes in `shared/mask-patterns.txt`: env files, private keys,
credential/token files, `secrets.*` configs and tfvars. To add patterns or exceptions for your
project, create `.devcontainer/mask-patterns.txt` (same format; `!` lines unmask), e.g.

```
^data/api-token\.txt$
!^certs/ca-public\.pem$
```

## Settings in `.env`

All template settings are `DEVCONTAINER_*` lines in the root `.env` on the host (masked in the
container, so the agent can't read or change them). They take effect at the next container start.

| Line | Effect |
|---|---|
| `DEVCONTAINER_GIT_SUBMODULES_WRITABLE=1` | Commits inside submodules, nested ones too: their gitdirs become writable, hooks/config/`modules/`/`worktrees/`/`commondir` stay read-only. See [security.md](security.md#protected-paths). |
| `DEVCONTAINER_EDITABLE_BY_AGENT=1` | Leaves `.devcontainer/` writable, for developing the template itself. **Removes a protection:** the agent can change what runs on your host at the next start. Don't use it in projects. |
| `DEVCONTAINER_LMSTUDIO_URL=http://<host>:1234` | LM Studio server for the host overlay (default `http://host.docker.internal:1234`). See [customizing.md](customizing.md#how-do-i-use-local-models-lm-studio). |
| `DEVCONTAINER_LMSTUDIO_MODELS_DIR=<path>` | Model folder for the sidecar overlay (default `~/.lmstudio/models`). |
| `DEVCONTAINER_<YOUR_NAME>=…` | Your own compose-time variables, e.g. mount sources in `compose.project.yml`. See [customizing.md](customizing.md#how-do-i-mount-other-files-or-folders-datasets-model-weights-). |

- **The two switches must match exactly** `NAME=1` on a line of its own: no spaces, quotes or
  `export`. Anything else counts as off. Both print a warning at every start while on.
- **Unprefixed lines never reach compose or the container;** `container.env` is the file for
  environment variables inside the container (see above).

## Optional overlays

### Optional: Docker access

Add `"../shared/compose.docker-proxy.yml"` to a variant's `dockerComposeFile` (before the host
overlay) to give the agent read-only Docker access (`ps`, `logs`, `inspect`; no `run`/`exec`/`build`).
It's off by default because `docker inspect` exposes the environment variables of **every**
container on the host. Never mount `/var/run/docker.sock` directly instead.

### Optional: local model (LM Studio)

`claude-local` runs Claude Code against local models served by
[LM Studio](https://lmstudio.ai) (≥ 0.4.1, Anthropic-compatible API). You can use it without a Claude
account, or next to one. It uses the same tools, permissions and protections; only the model
differs. Plain `claude` keeps talking to Anthropic. Add **one**
overlay to the variant's `dockerComposeFile` (before `compose.project.yml`) and rebuild:
- `compose.lmstudio-host.yml`: LM Studio/llmster runs on the host, reached at
  `host.docker.internal:1234`.
- `compose.lmstudio-sidecar.yml`: headless llmster in a GPU container on the dev network, using the host's
  model folder.

Setup, model choice and caveats: [customizing.md](customizing.md#how-do-i-use-local-models-lm-studio).

## Host detection

Host detection lives in `shared/host-override.sh`. Its output (`.devcontainer/.generated/`)
is gitignored. `initialize.sh` is bash 3.2 compatible (macOS). Supported hosts: see [getting-started.md](getting-started.md#before-you-start).

## System packages

Project apt packages go in `.devcontainer/apt-packages.txt` (all variants; ships empty and is
yours, template updates leave it alone) and/or
`.devcontainer/<variant>/apt-packages.txt` (one variant). The Python variants
ship a variant file with the **OpenCV runtime** (`ffmpeg libgl1 libglib2.0-0 libsm6 libxext6`);
edit or remove it for your project. Format: whitespace-separated, `#`
comments, optional version pins. Both files are read-only to the agent. Rebuild the container
after changing them.

```
# .devcontainer/apt-packages.txt
ffmpeg libsm6 libxext6        # OpenCV runtime
cmake=3.28.3-1build7          # pinned version
```

Pinned versions can disappear from the Ubuntu archive after updates, and the build then fails.
Pin only where you need to. The uv toolchain installs only Python build dependencies; the Docker
CLI is only installed with the docker-proxy overlay.

## Toolchains

A toolchain is a folder `shared/toolchains/<name>/`. Every file in it is optional:

| File | Runs | Purpose |
|---|---|---|
| `apt-packages.txt` | image build, as root | system packages, one or more per line, `#` comments |
| `install.sh` | image build, as the container user | user-level tools |
| `init-host.sh <env-file>` | host, before start | append env vars, create shared volumes |
| `post-start.sh` | container start | e.g. link venvs into volumes (run by `shared/post-start.sh` from `postStartCommand`) |
| `compose.yml` | — | overlay that adds volumes and environment variables |

A variant can combine toolchains: `initializeCommand` lists them in order (e.g.
`initialize.sh python-uv-cpu uv node`), and `dockerComposeFile` lists each one's `compose.yml`.
The image installs them in that order, and `shared/post-start.sh` runs their `post-start.sh` in
that order. `initialize.sh` warns if a listed toolchain's `compose.yml` is missing from the variant.

To add one (e.g. `conda`):
1. Create the folder.
2. Add it to a variant: its `compose.yml` in `dockerComposeFile`, its name in `initializeCommand`.

For conda, use Miniforge (conda-forge), not the Anaconda `defaults` channel, which has commercial terms.

### uv details

- **Venvs:** they live in a per-worktree volume. `post-start.sh` symlinks
  `<project>/.venv-<worktree>.ct` into it for every `pyproject.toml` under `/app`, and
  `UV_PROJECT_ENVIRONMENT` points uv at that link. `.gitignore` ignores these links and a plain
  `.venv`; the patterns have no trailing slash, because git treats a symlink as a file.
- **uv's Python installs:** they're shared across all projects in the external volume
  `claude-code-uv-python-versions`, which `init-host.sh` creates.

### node details

No variant ships with it; add it to one (see [customizing.md](customizing.md#how-do-i-use-node-npm-pnpm)).

- **Node versions:** [fnm](https://github.com/Schniz/fnm) (pinned, checksum-verified) switches to
  the version of the nearest `.nvmrc` / `.node-version` on `cd`, also in the agent's
  non-interactive shells. `post-start.sh` installs a default (latest LTS) and every version pinned
  under `/app`. Versions are shared across all projects in the external volume
  `agent-sandbox-node-fnm`.
- **npm, pnpm, yarn:** npm comes with Node; pnpm and yarn come through corepack, at the version in
  `package.json`'s `packageManager`. `post-start.sh` installs corepack where Node no longer
  bundles it (Node ≥ 25). The npm cache, corepack's downloads and the pnpm store are shared in
  the external volume `agent-sandbox-node-cache`.
- **node_modules:** every directory with a `package.json` (outside `node_modules` and hidden
  directories) gets its own volume `agent-sandbox-<worktree>-nm-<dir>`, mounted directly at its
  `node_modules`. They aren't symlinks like the uv venvs: npm/pnpm workspaces link packages with
  relative symlinks, which would resolve inside the volume. `init-host.sh` writes the mounts to
  `.generated/compose.node.yml`. It also creates the (empty) `node_modules` on the host, so Docker
  doesn't create it root-owned. A host-side `node_modules` is left alone and is only hidden in the
  container.
  - **A new package directory needs a rebuild** (new mount; the image creates the mount point, so
    the volume belongs to the user). Until then `post-start.sh` warns, and installs there land in
    the workspace.
- **Configuration:** a project `.npmrc` is masked in the container (it often holds tokens). Put
  settings in `container.env` as `npm_config_<key>=…` (npm's environment form; check your pnpm
  version's docs for which of these it reads). The pnpm store location is set in the image
  (`~/.config/pnpm/rc`).

### latex details

The `latex` variant ships with it; other variants can add it (see [customizing.md](customizing.md#how-do-i-write-latex)).

- **TeX Live 2023** from Ubuntu 24.04's packages, a curated set (`shared/toolchains/latex/apt-packages.txt`):
  the common LaTeX bundles (recommended, extra, science, pictures, publishers, bibtex-extra),
  LuaLaTeX and XeLaTeX, latexmk, biber, chktex, latexindent, epstopdf, Pygments. Not
  `texlive-full` or `texlive-fonts-extra`; add those to an apt list if you need them.
- **Nothing is persisted in volumes:** everything is in the image. `install.sh` builds LuaLaTeX's
  font database at image build, so the first `lualatex` run isn't slow after each rebuild.
  `~/texmf` (`TEXMFHOME`) exists but is lost on rebuild.

## Claude Code

Claude Code is installed at image build time. Rebuild the container to update it. Its config
persists in the volume `claude-code-<worktree>-config`.
